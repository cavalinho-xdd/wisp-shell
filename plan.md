## 🖥️ Multi-Monitor Support — ✅ BUILT (2026-07-28)

**Decision**: one pill + click-catcher pair per connected monitor, not primary-only lock. Matches the reference dotfiles' own convention — both `caelestia-dots` (`services/Screens.qml`, `modules/drawers/Drawers.qml`) and `nixos-configuration` (`scripts/quickshell/TopBar.qml`, `Floating.qml`) instantiate their bar/floating overlay windows per-screen via `Variants { model: Quickshell.screens }`, none of them lock to primary.

**Built** (`shell.qml`): the two top-level `PanelWindow`s (`clickCatcher`, `floatingPill`) are now the `delegate` of a `Variants { model: Quickshell.screens }`, wrapped in a `QtObject { required property var modelData }` so both windows share one `screen: screenRoot.modelData` source and can reference each other (`screenRoot.pill`/`screenRoot.clickCatcher`) despite being declared as sibling properties rather than plain children (`QtObject` has no default child property — `Item`'s `data` trick wasn't needed since named `property PanelWindow x: PanelWindow{...}` works directly and is the more common idiom for this).

**State split**:
- **Global** (unchanged): `core/Island.qml` singleton — media/notification content is identical on every monitor's pill, by design.
- **Per-monitor** (now correctly local): `isExpanded`, `expandTab`, `contentStack` depth — each monitor's pill opens/closes independently. Guaranteed by construction since these are plain properties on a `PanelWindow` instantiated once per screen, not touched by the refactor.

**One-time init moved**: the `hyprctl eval` layer-rule injection, launcher-keybind injection, and `Settings.ready` touch used to live in `floatingPill`'s `Component.onCompleted` — with N monitor instances that would fire N times (redundant `hl.bind` calls, etc). Moved up to `ShellRoot`'s own `Component.onCompleted`, which runs exactly once regardless of monitor count.

**Real per-monitor bug caught and fixed before it shipped**: `fullscreenOverride` originally read `Hyprland.focusedWorkspace.hasFullscreen` — compositor-global (whichever workspace currently has keyboard focus). Under the naive per-screen refactor this would've made fullscreening an app on monitor A also hide the pill on monitor B, since both instances shared the same global check. Fixed to `Hyprland.monitorFor(screenRoot.modelData).activeWorkspace.hasFullscreen` — `Hyprland.monitorFor(screen)` is a documented static invokable (verified in `~/coding/quickshell/src/wayland/hyprland/ipc/qml.hpp`), `HyprlandMonitor.activeWorkspace`/`HyprlandWorkspace.hasFullscreen` are both live IPC-bindable properties (`ipc/monitor.hpp`, `ipc/workspace.hpp`) — each monitor now checks only its own workspace.

**Verified live** (this machine: DP-1 2560x1440@164.8Hz + DP-2 1920x1080@60Hz): `qs -p shell.qml` loads with zero new QML warnings (only the pre-existing, documented `ii` DBus notification-server conflict). `hyprctl layers -j` confirmed exactly one `wisp`-namespaced layer surface per monitor, correctly centered top on each screen's own coordinate space (`905,12 750x550` on DP-1, `3145,12 750x550` on DP-2 — i.e. locally centered, not globally). `grim` screenshots of both outputs confirm both pills render correctly and share the same live MPRIS track (Island singleton content correctly identical across monitors) while being visually independent surfaces. Found and killed an unrelated stray leftover `qs -p .` process from an earlier session that was still running the pre-refactor code and briefly caused a duplicate `wisp` layer on DP-1 — not a bug in the new code, just stale process hygiene.
**Not conclusively verified**: interactive click-to-expand via `ydotool` (blind screen-coordinate clicks kept landing on the workspace-dot/clock sub-areas' own `MouseArea`s instead of the background one) — but `isExpanded` was already local per-`PanelWindow` before this change and nothing in the click-handling code path was touched, so this is low-risk; confirm by hand (click the pill on each monitor, expect independent expand/collapse).
**Known pre-existing limitation, unchanged**: `launcher.qml` (Big Future Task #2) is still a separate process that independently picks "whichever monitor is focused" at its own launch time — on a 2-monitor setup it can now visibly mismatch a specific pill's monitor if focus differs from where the user expects. Same caveat as already documented there, worth revisiting together if it starts to matter.

## ✨ UX Animation Pass — ✅ BUILT (2026-07-28)

Deliberately scoped to animations that **make the shell easier to use**, not decoration. Audit first: every component already had hover/press `Behavior`s (the CLAUDE.md micro-interaction rule was being followed), so the real gaps weren't missing polish — they were **missing state feedback on slow operations**.

**The gap: clicking a Wi-Fi network gave zero feedback.** `modelData.connect()` fired and the row sat completely unchanged until the connection either succeeded or didn't. The only way to know a click had registered was to wait and see. Bluetooth was nearly as bad: `pairing` was surfaced, but only as static text, and it was checked *after* `paired`, so connecting an already-saved device showed "Paired" — nothing changed at the exact moment the user most needed to know something was happening.

**New: `components/Spinner.qml`** — the project had no indeterminate progress indicator at all (only `CircularProgress`, which is determinate). `QtQuick.Shapes` arc with two behaviours that make it read as alive rather than as a rotating decoration: the sweep angle breathes as it spins (so it never looks like a static ring merely rotating), and it fades/scales in rather than popping (so an operation finishing in <200 ms never produces a visible flash). Gated on `running && visible && opacity > 0.01` — a spinner left animating behind a collapsed panel is a permanent repaint at 165 Hz for nothing (per this file's own 165 Hz pass).

**New: `components/ScrollFade.qml`** — edge fades on scrollable lists, applied to the Wi-Fi and Bluetooth scan lists. This is a *discoverability* fix, not decoration: a `clip: true` list cuts content off with a hard edge that looks identical whether the list ends there or continues, so "there is more below" was invisible until the user happened to scroll. The fade appears only at an edge that actually overflows, and its disappearance is what tells you you've hit the end. `enabled: false` so it never intercepts input from the list it describes.

**Applied**:
- Wi-Fi rows: signal icon ↔ spinner crossfade bound to `stateChanging`, subtitle becomes "Connecting…"/"Disconnecting…" in the accent colour. `Network.stateChanging` is a live bindable (`quickshell/src/network/network.hpp`), so this tracks the real operation rather than a guessed timeout.
- Bluetooth rows: same icon↔spinner treatment driven by `pairing || state === Connecting || state === Disconnecting` (`quickshell/src/bluetooth/device.hpp`), **and the status-text priority bug fixed** — in-flight states are now tested before `paired`/`connected`.
- Wi-Fi empty state: "Scanning…" used to sit perfectly still, indistinguishable from a hung scan; now paired with a spinner and a slow breathing opacity.

**New probe: `test_views.qml`, and it closes a real testing blind spot.** `qs -p shell.qml` does **not** catch errors in `WifiView`/`BluetoothView`/`AudioView`/`WallpaperView`: they live inside `Component {}` blocks that are only instantiated on click, so a broken subview loads perfectly clean and only explodes later, in front of the user. (This is the same shape as the `Qt.resolvedUrl` bug at the top of this file — deferred instantiation hiding breakage.) `test_views.qml` instantiates them directly in a `FloatingWindow`, turning that into a visible startup failure. **Run it after touching any StackView-pushed view.**

**🔴 Probe-sizing lesson — a bad probe produced a false "verified".** The first version of `test_views.qml` put `WifiView` and `BluetoothView` **side by side at 380px wide each**. These views are laid out for the expanded pill's **750x550**; at half that, content overflowed and the "Scan Networks" chip was visibly cut off past the left edge. That screenshot was then reported here as "both views render correctly" — it did not, and the user caught it. Two things went wrong and both are worth remembering:
1. **Probe at the component's real size.** A layout probe at the wrong dimensions tests a layout that will never exist, and its failures are indistinguishable from real ones.
2. **A screenshot showing visibly clipped content is a failure, not a pass** — the claim was written from "it instantiated without errors" while the image on screen disagreed. Read the image, not just the log.
Rewritten to render **one view at a time at the true 750x550**, with a `forceScanView` flag — because the info view the component opens on doesn't exercise the scan list where all of this pass's changes actually live, so the original probe wouldn't have covered them even at the right size.

**Verified (after the probe fix)**: Wi-Fi info view and scan view both render correctly at true size, nothing clipped, zero errors/TypeErrors. Connected row correctly shows the signal icon rather than the spinner (`stateChanging` false), and ScrollFade correctly draws no fade when the list doesn't overflow. The spinner/crossfade/fade behaviours themselves were confirmed in `test_polish.qml` (component gallery): spinner states incl. the not-running one correctly invisible, the idle-vs-connecting row crossfade, and ScrollFade's asymmetry (bottom faded, top not, while scrolled to top). **Still not verified end-to-end: an actual in-flight connect/pair on real hardware** — that needs a live connection attempt, which this session didn't perform. Interactive click-through of the live pill remains unreliable via ydotool; the `FloatingWindow` probe pattern from the polkit work is the way to verify UI here.

## 🔤 Fonts — ✅ BUILT (2026-07-28)

**The font this project thought it was using was never installed.** `"Iosevka Nerd Font"` was hardcoded 75× across 32 files as the icon font, and `fc-match "Iosevka Nerd Font"` on this machine returns **Noto Sans** — a font with no Nerd glyphs at all. The icons only ever rendered because fontconfig does *per-glyph* fallback below the family level: Qt asked for a family it resolved to Noto Sans, hit codepoints Noto Sans lacks, and fontconfig quietly sourced them from whatever else was installed (here `JetBrainsMonoNL Nerd Font`, first in `fc-match -s ":charset=f0134"`). So the icons were correct **by accident**, through a path that differs per machine and produces tofu on any install without some Nerd Font. This is Scaling Notes' "Font is assumed present, not verified" — except already broken here, not hypothetically elsewhere.

Second finding: **no text font was ever set.** All 75 `font.family` assignments were the icon font; the other ~124 `Text` elements had none, so every piece of body text rendered in the Qt/fontconfig default (Noto Sans). Nothing in the project ever chose a typeface for its own text.

**Chosen**: text = **Google Sans Flex**, icons/mono = **JetBrainsMono Nerd Font**. Both already installed — zero new dependencies. Google Sans Flex is what both of the most polished reference shells use (ii-dots `Config.qml` fonts.main/numbers/title; caelestia's `appearanceconfig.hpp` `sans`), it is variable (one file covers tooltip-size through headline cleanly), and [web consensus for 2026](https://www.designmonks.co/blog/best-fonts-for-ui-design) puts Inter as the general default with [Google Sans Flex specifically endorsed as a Linux system UI font](https://www.omgubuntu.co.uk/2025/11/google-sans-flex-font-ubuntu); Inter is ~85% similar but is *not* installed here, so it would have been a new dependency for a marginal difference. For reference, the other repos: nixos-configuration uses Inter + JetBrains Mono, iNiR uses Space Grotesk / Roboto Flex.

**Centralized in `core/Theme.qml`** as `fontFamily` / `fontIcon` / `fontMono`, each resolved at startup by `pickFont(candidates, fallback)` walking `Qt.fontFamilies()` — not hardcoded. This is the direct fix for the failure mode above: a missing font otherwise fails *silently and invisibly* (Qt renders something, nothing warns), whereas explicit resolution degrades to a chosen second choice and logs what it picked (`Theme fonts -> text: … | icon: … | mono: …` at startup). Also closes Settings Gap Analysis item 4 — a font picker is now one `settings.json` field away instead of a 75-site refactor.

**Applied**: 75 icon sites → `Theme.fontIcon` (sed); 131 text sites → `Theme.fontFamily`, inserted by a brace-counting Python script (in scratchpad) rather than regex, so a `Text` containing a nested `Text` that sets a family still got its own. Skipped: `core/Theme.qml` (own comment), `test_glyph.qml` (a deliberate glyph probe), and any block using the grouped `font { … }` form (flagged for a human, none hit).
- **Script bug caught by the load test**: for the single-line `Text { text: "x"; … }` form the inserted property landed on the same line as the rest of the block, producing `font.family: Theme.fontFamily text: …` → `Expected token ';'`, which broke `ExpandedDashboard.qml` and therefore `shell.qml`. Fixed by always emitting a trailing `;` (valid QML in both the single- and multi-line case), restoring from backup and re-running rather than hand-patching. **Lesson: mechanical QML edits must assume the single-line object form exists.**
- **Verified**: all five entry points load with zero errors; live screenshots confirm text in Google Sans Flex and Nerd glyphs (media controls, clock, EQ bars) rendering from the now-correctly-declared icon font.

**Process note**: `lock.qml` was carelessly included in a batch load test — per CLAUDE.md that **locks the session immediately**. The 6 s timeout killed it and `loginctl show-session … LockedHint` confirmed `no` with no lock surface left, so no harm done, but `lock.qml` must be excluded from any "load every entry point" loop.

## 🔐 Polkit Agent + Mixer Polish — ✅ BUILT (2026-07-28)

**Polkit agent** (`components/PolkitDialog.qml` + wiring in `shell.qml`): Quickshell has a real native `Quickshell.Services.Polkit` module — `PolkitAgent` (registers as *the* session agent, exposing `isActive`/`isRegistered`/`flow`) and `AuthFlow` (`message`, `actionId`, `iconName`, `identities`/`selectedIdentity`, `isResponseRequired`, `inputPrompt`, `responseVisible`, `supplementaryMessage`/`supplementaryIsError`, `failed`, `submit()`, `cancelAuthenticationRequest()`). API read from source + `module.md`, never guessed; upstream ships a reference implementation at `~/coding/quickshell/src/services/polkit/test/manual/agent.qml`. No external binary needed — this replaces `polkit-gnome`/`polkit-kde-agent` entirely.

- **Placement**: deliberately NOT inside the per-monitor `Variants` block. A privilege prompt is modal and singular; N copies across N monitors would mean N surfaces each demanding `WlrKeyboardFocus.Exclusive` and fighting over it. One dialog, `Exclusive` focus (not `OnDemand` — with OnDemand the typed password could land in whatever window actually held focus).
- **Anti-phishing**: the dialog shows polkit's `actionId` verbatim alongside the human message. Any app can *trigger* a request and influence the message text, but not the action id — so that's the part that actually tells the user what they're authorizing. All request-supplied strings render as `Text.PlainText`, never rich text.
- **🔴 The retry mechanism was removed — it segfaulted the whole shell.** Originally a `Loader` toggled by a 30 s timer, so destroying and rebuilding `PolkitAgent` would re-run registration (see the next bullet for why a retry seemed necessary). Caught live: after several retry cycles the shell died with SIGSEGV, log showing `QEventLoop: Cannot be used without QCoreApplication` immediately before the crash, plus a report under `~/.cache/quickshell/crashes/`. Cause is in Quickshell: destroying a `PolkitAgent` calls `PolkitAgentImpl::onEndOfQmlAgent` → `delete instance` (`agentimpl.cpp`), which tears down the process-wide GLib/GDBus listener; doing that repeatedly — and especially while the app is shutting down — is not safe. Now a plain always-alive `PolkitAgent`, verified with a 45 s run: zero crashes, exactly one registration attempt, no `QEventLoop` errors. **Crashing the entire shell is far worse than lacking an agent in a session where another one already holds it.** Do not reintroduce a retry without an upstream fix. Worth an upstream issue.
- **Registration conflict**: polkit permits exactly one agent per session. Probe (`test_polkit.qml`) confirmed this host refuses ours outright while ii runs — `"An authentication agent already exists for the given subject"`. Worse, **Quickshell's polkit listener does not retry**: `listener.cpp` makes a single `polkit_agent_listener_register` call at `componentComplete`, logs one warning, and gives up forever — unlike the notification server, which retries itself (its log even says so). So a wisp started while anything else holds the agent would silently have no agent for the whole session. Worked around by wrapping `PolkitAgent` in a `Loader` and toggling `active` off/on from a 30 s timer while unregistered — destroying and rebuilding the object re-runs registration, so wisp picks the agent up whenever the other one exits. Interval is deliberately slow: the only recoverable event is another agent quitting (rare, not latency-sensitive) and each failed attempt logs a warning.
- **⚠ Not verifiable end-to-end on this host**: a real `pkexec` prompt can't reach wisp while ii owns the agent, exactly like the notification-server conflict (Big Future Task #1). UI verified instead via `test_polkitui.qml` (fake flow state, same trick `test_lockui.qml` uses for the lock screen) — screenshot-checked: shield badge, message, action id, identity chips, password pill, cancel.

**Two bugs found and fixed during the review of the above**:
1. **Password field never reliably got keyboard focus.** Focus was claimed only from `onResponseRequiredChanged` — but when `responseRequired` arrives as an *initial property binding*, that handler runs during component init, before the window is mapped, and the `forceActiveFocus()` is silently lost. Observed as nondeterministic "typing does nothing" in the isolation probe. Fixed with `Component.onCompleted: forceActiveFocus()` plus re-assert on focus loss — exactly what `LockContent.qml` already does, for the same reason. **Lesson**: `Component.onCompleted` is the reliable hook for initial focus; a property-change handler is not, when the property's first value comes from a binding.
2. **A "double keystroke" scare that turned out to be the test harness, not the code** — worth recording so nobody re-chases it. Driving a `WlrKeyboardFocus.Exclusive` layer-shell surface with `ydotool` gave non-reproducible results: two runs showed every character and every Enter arriving twice (3 typed chars → `len: 6`, one Enter → two submits), later runs received no keys at all. Root cause was concurrent leftover probe processes sharing one layer-shell namespace and both holding exclusive focus. Confirmed by switching the probe to a plain `FloatingWindow` (ordinary compositor focus, which is also why upstream's own manual polkit test uses one): with a single verified process, "abc" + one Enter produced **exactly one submit, len 3**, and Escape produced exactly one cancel. **Lesson for this repo: do not keyboard-test layer-shell surfaces via ydotool** — use a `FloatingWindow` probe for input-behavior tests, and always confirm no other probe process is alive first (`ps -eo pid,cmd | grep wisp-shell`).

**Per-app volume mixer — already existed, survey was wrong.** The Daily-Driver Feature Survey below lists this as Tier-1 gap #5 (from the caelestia/ii-dots fork research). It isn't: `components/AudioView.qml` has had "Applications" and "Recording Applications" sections bound to `Audio.outputAppNodes`/`inputAppNodes` all along, rendered by `components/PwNodeDelegate.qml`, which correctly carries its own per-node `PwObjectTracker`. Verified live via `test_appnodes.qml` and a screenshot of the real view: 3 output devices, 1 input, and the running browser at 37%. The probe also re-demonstrated the CLAUDE.md gotcha concretely — without a `PwObjectTracker`, an audibly-playing stream reports `volume: 0`; with one, the true 37%. **Treat the survey's gap list as leads to verify, not facts** — it was compiled by agents reading other repos, not this one.

**Mixer polish pass** (`PwNodeDelegate.qml`) — these rows were the one interactive surface in the shell with zero micro-interaction, against CLAUDE.md's own UI rule: added whole-row hover (border tint + 1.012 scale), entry fade+rise, muted-state dim, hover/press spring on the device-select chip (plus the `PointingHandCursor` it was missing), and a counting percentage readout that animates with the slider fill instead of snapping.
- **Bug caught while writing it**: first draft assigned `opacity` twice — once for the live muted dim, once as the entry animation's starting value. The second assignment silently replaces the first binding, so the muted dim would have died the moment the intro ran. Fixed by keeping them as separate factors (`introOpacity * (nodeMuted ? 0.55 : 1.0)`), a one-shot property multiplied into a live binding.

**Also noted**: `cliphist` and `wl-clipboard` are already installed and running on this host (ii uses them — `wl-paste --watch cliphist store` is live), so Tier-2 item #8 (clipboard manager) needs no new package after all, just the QML.

**Stale section warning**: Known Bugs #1 in this file (the `IconButton` self-toggle severing external bindings) describes code that no longer exists — `components/IconButton.qml` now only emits `clicked()` and never mutates its own `isChecked`. That entry, and possibly others in that list, are already fixed; re-verify before acting on any of them.

## 🔋 Battery + Tray + OSD Popups — ✅ BUILT (2026-07-28)

First three Tier-1 items off the Daily-Driver Feature Survey below. All native Quickshell services or purely reactive to state wisp already tracked — zero new external dependencies.

**Battery** (`core/Battery.qml`, new singleton): facade over `Quickshell.Services.UPower`'s `displayDevice`. Gates `available` on `isLaptopBattery`, not just `isPresent`/`ready` — UPower's `displayDevice` is a synthetic aggregate that exists even on hardware with zero batteries, so this is the difference between correctly hiding on a desktop and showing a fake 0%-forever indicator (same principle already flagged in Scaling Notes for the GPU ring on non-Nvidia machines). Exposes `percentage`/`charging`/`fullyCharged`/`low`/`critical`/`icon()` (10-step Nerd Font glyph ramp, separate charging/discharging sets). Rendered as icon+percentage in `CollapsedBar.qml`, next to the clock, opacity-gated on `available` so it's fully invisible (not just empty) on non-laptop hardware.

**System tray** (`components/TrayItem.qml`, new): facade-free — `Quickshell.Services.SystemTray` is used directly, no wrapper singleton needed. Left-click `activate()`, right-click opens the item's real DBus menu via `QsMenuAnchor` (native platform menu rendering, no hand-rolled menu widget — `anchor.window: root.QsWindow.window` gets "the window this Item lives in" automatically, needed since `TrayItem` is used from `ExpandedDashboard.qml`, a separate file/Component from whichever per-monitor `floatingPill` instance renders it, so `floatingPill`'s own `id` isn't reachable across that boundary). Mounted as a `Repeater` in `ExpandedDashboard.qml`'s header, between the uptime readout and the reload/settings/power icon cluster.
- **Real bug hit and fixed**: initially wrote `Repeater { model: SystemTray.items; delegate: TrayItem { trayItem: modelData } }` — QML warning at runtime: `Unable to assign QuickshellScreenInfo to qs::service::sni::StatusNotifierItem`. Root cause: this Repeater is nested inside the outer per-monitor `Variants { model: Quickshell.screens }` in `shell.qml` (the Multi-Monitor Support work above), which *also* injects a same-named `modelData` — the inner Repeater's `modelData` resolved to the outer Variants' screen object instead of its own delegate's tray item. Fixed by indexing `.values` explicitly (`model: SystemTray.items.values.length`, `delegate: TrayItem { required property int index; trayItem: SystemTray.items.values[index] }`) instead of relying on the bare `modelData` name. **General lesson**: any Repeater/Variants nested inside the new per-screen Variants block is at risk of this exact collision — prefer index-based `.values[index]` access over unqualified `modelData` for anything declared inside `ExpandedDashboard.qml` or its children.
- **Verified live**: real Discord tray icon (with unread-badge) rendered correctly in the header once the fix landed; zero QML warnings after.

**OSD popups** (`core/Osd.qml` new singleton + `components/OsdPopup.qml`): purely reactive, **no hyprctl keybind wiring at all** — hardware volume/mic keys already go through Pipewire (`wpctl`/`pactl`), which `core/Audio.qml` already tracks live, so `Osd.qml` just watches `Audio.volume`/`muted`/`micVolume`/`micMuted` via `Connections` and exposes a single transient "what changed last" slot (`reason`/`value`/`muted`/`shown`), auto-hiding 1.6s after the last change. A `ready` flag gated by a 400ms startup `Timer` prevents Pipewire's async initial node population from firing a spurious OSD at shell launch (same class of lazy-init gotcha `Island.qml` already documents for Mpris). Rendered in its own small (220×64) `PanelWindow` per monitor — bottom-anchored, 140px margin — deliberately a separate surface from the main pill so it never interacts with the pill's collapsed/media/expanded width state machine.
- **Scope cut, deliberate**: volume + mic only, no brightness OSD yet. Brightness needs a new `core/Brightness.qml` service backed by `brightnessctl` (no native Quickshell brightness service exists — confirmed via source grep, unlike UPower/SystemTray/Polkit which do), and this dev machine has no laptop backlight to test against (desktop, two external DP monitors) — shipping an unverifiable feature silently would repeat the exact mistake the GPU-ring/Battery-availability principle above exists to avoid. Natural follow-up once there's hardware to verify on.
- **Verified live**: `wpctl set-volume @DEFAULT_AUDIO_SINK@ 5%+/-` and `wpctl set-mute ... toggle` both correctly triggered the popup (icon, animated fill bar, percentage text; mute state shows red icon + empty bar + "--"), on the correct per-monitor position, with correct auto-hide timing.

**Also fixed in passing**: `core/Osd.qml`'s first draft omitted `import Quickshell` (only had `import QtQuick` + `import "."`) — failed to load with `Singleton is not a type`, since the `Singleton` QML element itself comes from the `Quickshell` module, not implied by the sibling-singleton-reference `import "."`. Every other `core/` singleton already has this import; only the brand-new file was missing it.

**Process hygiene note**: mid-session, `hyprctl layers -j` briefly showed two `wisp`-namespaced surfaces on DP-1 with two different PIDs — not a code bug, an orphaned `quickshell` process from an earlier failed background-launch attempt in this same session (this environment's backgrounding occasionally detaches a process without the tracking shell noticing exit status). `ps -p <pid> -o cmd` + `/proc/<pid>/cwd` confirmed which one was stale before killing it. Worth checking `hyprctl layers -j` for duplicate `wisp` PIDs if a future test session ever looks visually "doubled" for no code reason.

**Review pass, same day**: self-reviewed the three new files/edits above before considering the feature done, found and fixed 3 real bugs (none caught by the earlier live testing since none of them produce a visible symptom under normal manual testing):
1. **OSD had no fullscreen suppression.** The main pill fades out and drops its input mask during fullscreen (`fullscreenOverride`, Multi-Monitor section above) specifically so a fullscreen video/game's own controls stay clickable underneath. The new OSD window had none of that — adjusting volume mid-fullscreen-video would've drawn a 220×64 popup **and** silently eaten clicks in that screen region for 1.6s every time, since an unset `mask` defaults to the full window rect. Fixed with the same per-monitor `Hyprland.monitorFor(screen).activeWorkspace.hasFullscreen` check the pill already uses, but simpler: OSD has no fade choreography to preserve, so `visible: Osd.shown && !fullscreenOverride` alone (fully unmapping the surface) is sufficient — no separate mask-swap needed like the pill required.
2. **`Osd.ready`'s 400ms startup timer was a race, not a guard.** A fixed delay either fires too early on a slow boot (Pipewire's async node population hasn't finished — the first real volume read then looks like a "change" from the 0.0 fallback, popping a spurious OSD, the exact bug the timer existed to prevent) or is needless dead time on a fast one. Replaced with `sinksPopulated: !!(Audio.sink && Audio.sink.audio) && !!(Audio.source && Audio.source.audio)` — reactive to the actual PwObjectTracker-backed population Audio.qml already exposes — plus a 50ms settle `Timer` fired only once population is confirmed, to absorb the same-tick ordering race between "sink populated" and its first `onVolumeChanged`. Bounded relative to a real event now, not a blind absolute guess.
3. **Tray `onlyMenu` items had a dead left-click.** Quickshell's own doc comment on `StatusNotifierItem.onlyMenu` says plainly "activation will do nothing" for such items, but `TrayItem.qml`'s left-click handler called `.activate()` unconditionally regardless. Fixed: left click now opens the menu instead when `trayItem.onlyMenu` is set, matching the check nixos-configuration's own `TopBar.qml` already does (`modelData.isMenuOnly || modelData.onlyMenu`).

Re-verified live after fixes: zero new QML warnings, OSD popup + tray icon (Discord) both still render correctly post-fix. Fullscreen-suppression logic itself could not be live-verified end-to-end — same pre-existing limitation already documented in the Pill/Hyprland Interaction section (`hyprctl eval 'hl.dsp.window.fullscreen(...)'` doesn't reliably flip `hasFullscreen` on this host's Hyprland build) — but it reuses the exact `Hyprland.monitorFor`/`activeWorkspace.hasFullscreen` code path already live-proven correct for the main pill earlier in this same session, so confidence is high despite the untestable end-to-end path.

## 🎨 Design Audit vs published research — ✅ DONE (2026-07-28), findings in DESIGN.md

Web research pass on how shell/OS UI is actually designed, and on the now-recognisable "AI slop" look, then measured against the shipped code. **Full write-up lives in `DESIGN.md`** (§10–15) — that file was already a good description of the current system but had gone stale (still claimed "Iosevka Nerd Font" and "body text sets no font.family", both undone by the Fonts pass; described matugen as a plan; listed the deleted `WallpaperView` as a subview). Facts corrected, audit appended.

**Frame that settles design arguments** (from the peripheral-display and calm-technology literature): the collapsed pill is a *glanceable peripheral display*, and its quality metric is how little time and how few gaze transitions a read costs — not beauty. Two consequences: motion while idle is a *cost* not a feature, and web guidance like "body text ≥16px" does not transfer to a shell (GNOME's system font is 16px, macOS's menu bar ~13px), though contrast targets do.

**Measured findings** (all numbers from grep/APCA calculation, not estimates): 44 × `border.width: 1` where the published ladder is whitespace → 3-5% lightness shift → elevation → *then* border (A1); **no scales** — 24 distinct type sizes, 15 radii, 25+ durations against only 2 duration tokens in Theme (A2); **real contrast failures** (A3); body copy dense even for a shell (A4); hue count fine (A5); **one easing curve driving 45% of all motion** — `easeSpring`/`OutBack` 74 of ~165 animations, the structural twin of the "same fade-in on everything" slop tell, and the biggest visual-identity risk (A6); infinite idle animation loops on always-visible surfaces (A7).

**AI-slop scorecard**: clean on font choice (Google Sans Flex, Inter explicitly rejected), no glassmorphism/neon/gradient-orbs/bento, no dead hover states, real 60/30/10 tonal structure. Flagged: permanent dark default, lavender `#cba6f7` accent (defensible — Catppuccin Mauve predates the slop era and matugen replaces it, but it is exactly the hue reviewers pattern-match), the 44 borders, and A6's sameness.

**Applied this session (the only objectively-broken finding; everything else is a taste call left to the user)**: `Theme.outline` #45475a → #7f849c and `Theme.subtext0` #a6adc8 → #bac2de.
- `outline` measured **APCA Lc 10.4 on background / 5.4 on surface** against a ≥30 target for non-text UI — the shell's 44 borders were *simultaneously noisy and invisible*, adding nothing. Now Lc 36.2/31.2, clears the target on both.
- `subtext0` measured Lc 57.3/52.3/45.8 vs a ≥75 body-text target at the 10–13px sizes it is actually used at; now 69.2/64.2/57.6. **Honest limitation recorded in Theme.qml: ≥75 is unreachable on this palette** — even promoting it to the full `text` colour only reaches 69.5 on surface0, and would erase the primary/secondary distinction. On a dark palette you cannot have both "visibly dimmer than primary" and Lc ≥75; the real remedy is A4 (stop using this colour at 10–11px so the ≥45 large/bold target applies).
- Verified: all five entry points load with zero warnings; screenshot of the settings app confirms labels read clearly and the now-visible borders are not garish.

**Then: welcome wizard rebuilt borderless — ✅ DONE (2026-07-28).** User's verdict on the audit was that **the card borders are the strongest AI tell**, so the wizard was redesigned as the reference implementation of the separation ladder. Full before/after table in **DESIGN.md §16**; the short version:
- **Every decorative border gone** from `welcome.qml` and all five step components, plus the shared `components/ActionButton.qml` (which also de-borders the settings app's buttons).
- **Card-in-card nesting removed**, which is its own documented tell: the intro's preview list and the Ready step's system check were each a bordered `surface` box sitting inside the wizard's own card. Both containers deleted. The preview list is now four rows grouped by proximity; the system check gives each *row* the `surface` fill at 4px apart, since row-from-row is what actually needed separating.

Both now use fill — active scheme chips take a `Qt.alpha(primary, 0.22)` tint so the chip *becomes* the accent rather than wearing it. Hero badge likewise: tinted fill instead of a 2px ring around a neutral box.

Fixed with the verified `Item` wrapper + `anchors.fill` pattern rather than another `Layout.alignment` that would be ignored.

**Then: de-bordering applied shell-wide — ✅ DONE (2026-07-28).** Full table in **DESIGN.md §17**. `Theme.outline` is no longer used as a border anywhere in the shell except two colour-swatch rows, where it is functional (near-black swatches would be invisible without an edge).

1. `Failed to start discovery ... ## 🎉 First-Run Welcome Wizard — ✅ BUILT (2026-07-28)

Closes the Scaling Notes "No first-run experience" bullet. `welcome.qml` is the 6th entry point: a fullscreen setup wizard shown once, the first time wisp starts on a machine.

**Research first (no fork — 4 repos grepped directly).** Three distinct shapes exist in the references:
- **ii-dots** (`welcome.qml`, 493 lines) — one long scrolling `ApplicationWindow` of ordinary settings sections, with a "Show next time" switch in the titlebar. Cheapest.
- **iNiR** (`welcome.qml`, 1837 lines) — a 5-step wizard (Welcome / Appearance / Layout / Features / Ready) on a **fullscreen layer-shell overlay** with a blurred-wallpaper scrim, exclusive keyboard focus, a `StackLayout` with direction-aware step transitions, and a staggered scrim-then-card entry gate. Step 1 carries a "what you'll dial in" preview list, which its own comment explains is there so users see the value *before* they see the Skip button.
- **nixos-configuration** (`GuidePopup.qml`, 1599 lines) — a feature *tour* with screenshot previews. Shows off features rather than configuring anything; not a first-run flow, and not what was wanted here.

Both welcome apps share the same trigger: a sentinel file (`~/.local/state/.../first_run.txt`), checked at startup — ii-dots via `FileView.onLoadFailed(FileNotFound)`, iNiR via a `test -f` Process.

**Built: iNiR's shape, wisp's trigger.** The wizard reads as an event rather than "the settings app again", which is the point of a first-run flow — and wisp already owned every piece: `lock.qml`'s blurred-wallpaper `MultiEffect` backdrop, `launcher.qml`'s exclusive-focus overlay, and the settings app's `Cfg*` controls, reused verbatim so a setting can never drift between the wizard and Settings.
- **Trigger is a settings.json field, not a second sentinel file**: `shell.welcomeSeen` (default false). A machine that has never run wisp has no settings.json at all, so the field reads its default and the wizard fires — the same signal as the reference sentinel, with no extra file and no second existence-check mechanism, since wisp already keeps all state in one project-local file with a FileView on it. `core/FirstRun.qml` (new singleton, registered in `core/qmldir`) owns the decision; `shell.qml` touches it once at startup.
- **The one hazard of that choice, handled**: for the first instant of startup `Settings.conf` returns declared defaults, and `welcomeSeen`'s default is false — indistinguishable from a real first run, so reading it early would relaunch the wizard on *every* boot. Everything gates on `Settings.ready`. That flag turned out to be **left false forever on the FileNotFound path** — i.e. exactly the first-run case it now has to signal — so `Settings.qml` now sets `ready = true` there too ("settled", not "a file was read").
- **Steps**: Welcome (hero + preview list) → Appearance (dynamic colors, dark/light, 6 scheme chips, live palette swatches, transparency) → Wallpaper (folder + **live thumbnail strip of what's actually in it**, click to apply) → Shell (12/24h, workspace dots, weather, which monitor) → Ready (system check + keybind tips). Skip and Finish both mark it seen; getting it back is a "Show welcome again" button added to Settings → Advanced, not a re-prompt.
- **System check on the last step** is the concrete version of Scaling Notes' "detect GPU vendor, confirm the Nerd Font resolved": one `bash` process `command -v`-ing every binary wisp actually shells out to, plus a font check needing no subprocess (`Theme.fontIcon !== "monospace"` — Theme already resolves against `Qt.fontFamilies()` and falls back to a literal). Non-required misses render amber, not red, because a missing optional dependency is information rather than an error. **Verified live and it immediately earned its place**: correctly flagged swww/hyprpaper as missing on this host, which matches this file's own Phase 4 note.

**🔴 Two long-standing silent bugs found while wiring this up — both were shipped and broken.**
1. **`Qt.resolvedUrl()` cannot resolve a `.qml` path at all, and the earlier fix for this was wrong.** The "Fixed (2026-07-28): Settings/Lock/Night-Mode buttons were silently no-ops" section above diagnosed this as a difference between *dynamically-instantiated components* and *singletons*, and fixed it by moving the calls into `core/Settings.qml`. That diagnosis was wrong. A probe printing every path property **from the singleton** returned `configPath` (`.json`) as a real absolute path but `settingsAppPath`, `lockAppPath` and `wallpaperAppPath` (all `.qml`) as `qs:@/qs/...`. The split is by **file type**, not call site — so the settings gear and, far worse, **the power-menu Lock button had remained non-functional this entire time**, exactly as originally reported. A second probe confirmed the same from an entry-point root, ruling out context entirely. Fixed properly with `Quickshell.shellPath()` (the intended API — both ii-dots and iNiR use it for precisely this), applied to every path constant. Rule written into CLAUDE.md.
2. **The Super+Space launcher keybind had never worked.** `shell.qml` injected it with `Qt.resolvedUrl("launcher.qml")` — same bug, so `hl.bind` was pointing at `qs -p qs:@/qs/launcher.qml` since the launcher was built. Also fixed via `Quickshell.shellPath()`. Verified end-to-end afterwards: `ps` shows the spawned process with a real absolute path.

**Also found: `Layout.fillWidth` is silently ignored on a nested `ColumnLayout`.** The wizard's header and all five step components rendered collapsed and flush-left despite `Layout.fillWidth: true`. An isolated probe pinned it down: inside a 560px parent `ColumnLayout`, a nested `ColumnLayout` with `fillWidth` measured **60px** (its widest child) while a sibling `RowLayout` with the identical property measured the full **560** — and a `StackLayout` child behaved the same way. `Layout.minimumWidth` does not help; `Layout.preferredWidth: parent.width` and an `Item` wrapper with `anchors.fill` both do. ## 🔴 Fixed (2026-07-28): Settings/Lock/Night-Mode buttons were silently no-ops

**Symptom**: user clicked the header settings gear — no error, no window, nothing. Diagnosed by adding a `console.log` right before the `execDetached` call and asking the user to click again with their terminal visible.

**Root cause**: `Qt.resolvedUrl("../settings.qml")` called from *inside `ExpandedDashboard.qml`* — a component instantiated via `Component { ExpandedDashboard {...} }` + `StackView.replace()` in `shell.qml`, not loaded as a `qs -p` entry point directly — resolves against Quickshell's internal virtual module scheme (`qs:@/qs/settings.qml`) instead of a real `file://` path. The existing `.replace("file://", "")` was therefore a silent no-op, and the button was launching `qs -p qs:@/qs/settings.qml` — a path that doesn't exist — inside a fully detached process with no stdout/stderr wired to anything, so the failure was invisible everywhere. Confirmed via an isolated probe: the exact same `Qt.resolvedUrl` call made from a plain `readonly property` inside a **singleton** (`core/Settings.qml`, loaded once via `qmldir` at engine init) resolves correctly to a real absolute path.

Grepped the rest of `ExpandedDashboard.qml` for the same pattern and found **two more real instances of the identical bug**, one of them security-relevant:
- **Power-menu Lock button** (`cmd: ["qs", "-p", Qt.resolvedUrl("../lock.qml")...]`) — this means the Lock action built in Big Future Task #3 has likely **never actually locked the session** since it was wired up; it silently no-opped exactly like the settings gear, just with far higher stakes (a "Lock" button that doesn't lock).
- **Night Mode toggle**'s `fade_nightmode.sh` script path — also silently never ran.

**Fix**: added `Settings.settingsAppPath`, `Settings.lockAppPath`, `Settings.nightmodeScriptPath` as eagerly-resolved `readonly property string`s on the `core/Settings.qml` singleton (same pattern as the existing `configPath`), and pointed all three call sites at those instead of resolving locally. Also switched the spawned binary to the absolute `/usr/bin/qs` rather than bare `"qs"` while in there, to eliminate PATH resolution as a variable entirely. Verified all three properties resolve to real absolute paths via an isolated probe; `qs -p shell.qml` loads clean.

**General lesson for this codebase**: any `Qt.resolvedUrl()` call inside a component that gets instantiated via `Component {} + StackView.replace()/push()` (rather than loaded directly as a `qs -p` entry point) is suspect — resolve such paths in a singleton instead. Grepped every other `StackView`-pushed view (`WifiView`, `BluetoothView`, `AudioView`, `WallpaperView`, `CollapsedBar`) for the same pattern — none of them use `Qt.resolvedUrl` at all, so this was fully contained to `ExpandedDashboard.qml`.

- **Settings-UI pattern for "what's themeable"**: iNiR's `ThemesConfig.qml` uses a master `ConfigSwitch` per category (e.g. "Enable Terminal Theming") gating a `visible:` block of individual per-app switches underneath (one bound boolean per terminal/tool: kitty, alacritty, foot, starship, btop, etc.), all backed by nested JSON config keys. - **Also noted, lower priority**: iNiR themes Zed, VS Code forks, Chrome/Chromium, Spicetify, SDDM login screen, Steam, and Firefox (materialfox) — all via the same manifest+module pattern (`scripts/colors/targets/<id>.json` declaring id/label/category/backing-module/required-inputs, dispatched by `applycolor.sh`). Not relevant to qmlshell today (no equivalent apps in scope), but the manifest-registry *pattern itself* — a declared list of {id, label, themeable-or-not, backing mechanism} — is worth stealing later if the theming settings page grows past a handful of hardcoded switches.

**Terminal/fish OSC theming — ✅ BUILT (2026-07-28)**: implemented the terminal-agnostic OSC approach from the iNiR research above.

## 💡 Feature Ideas — Fluidity & "Dynamic Island" Behavior

The pill currently only has two sizes (collapsed bar / expanded dashboard). A real dynamic-island feel needs a *third* state: a transient, auto-sizing "live activity" strip that appears without a full expand.

- **Live-activity strip**: a small content area in `CollapsedBar.qml` that morphs to show whatever's most relevant right now — media track scrubbing across on song change, a volume/brightness flash on keybind, a download/update progress bar — then auto-collapses after N seconds. Model it as a priority queue (media > volume/brightness OSD > notification > idle-clock) so only one thing shows at a time and higher-priority events interrupt lower ones. This is the actual "island" behavior, not just resizing for dashboard vs. bar.
- **OSD popups as their own tiny `ShellRoot`**, same pattern as `wallpaper.qml` — a standalone transient panel triggered by an `IpcHandler` (Quickshell has this) so Hyprland keybinds (`bindl = ,XF86AudioRaiseVolume, ...`) can poke the shell directly instead of everything routing through the always-open main pill.
- **Shape morphing**: right now collapse/expand is just `implicitWidth`/`implicitHeight` + `radius` behaviors on a `Rectangle`. `caelestia-dots/components/widgets/WavyTopRect.qml` builds an actual wavy edge with `QtQuick.Shapes`/`PathSvg` — worth stealing for the transition edge between collapsed and expanded state instead of a plain rounded rect, if a more "liquid" identity is wanted for the distro's signature look.
- **Persisted UI state**: last active tab, last panel width/whether it was left expanded, pinned widgets — via the same `Persistent` singleton pattern proposed for settings above, so the shell resumes the layout state across restarts instead of always booting collapsed.
- **Real notification popups**: currently notifications only exist inside the expanded Dashboard tab (mocked). A proper implementation would pop a `NotifData`-style card briefly over the collapsed bar itself — this is the single biggest "does it feel alive" win available, since notifications are the most frequent live-activity trigger on a real desktop.

### iOS-style Dynamic Island — feasibility research (2026-07-27)

Real iOS Dynamic Island has 4 states: **compact-leading/trailing** (default single-activity view, split left/right across the pill notch), **minimal** (2 activities, one attached to the pill + one detached as a small circle), **expanded** (touch-and-hold, full detail card). Apple doesn't draw to it directly — apps define a Live Activity via ActivityKit/WidgetKit and the system auto-renders compact/minimal/expanded from that one data model. Confirmed doable here — maps onto architecture already in place, not a rewrite:

- **Media strip** (cava-viz or scrubbing bar during playback): data already flows — `Mpris.players` is wired in `MediaCard.qml`. Just needs a compact-mode presentation in `CollapsedBar.qml`. Cheapest win, no new dependency.
- **Notification icon flash**: `NotificationServer` + grouping already built in `components/NotificationCard.qml` (Phase 5 above). A `Connections { onNotification: ... }` hook feeding the live-activity strip is small, additive wiring — not new plumbing.
- **Priority queue + auto-collapse timer**: real new logic, doesn't exist yet in any form. This is the part that makes it feel like an actual dynamic island instead of "a strip that shows random stuff" — model as: media > volume/brightness OSD > notification > idle-clock, one Timer per active item, higher priority preempts.
- **Cava audio visualizer**: needs a `Process` piping `cava`'s raw output (ncurses-free mode exists for this) — new external binary dependency, not currently used anywhere in the project. Cosmetic only; do last.
- Third pill-size tier is one more branch on the existing `implicitWidth`/`implicitHeight` expressions in `shell.qml` (already derived from `isExpanded` + `contentStack.depth`) — no new sizing architecture required, just a new state value.

**Suggested build order**: media strip → notification icon flash → priority-queue/auto-collapse timer → cava viz.

**Media strip — ✅ BUILT** (2026-07-27, `core/Island.qml` + `components/IslandMediaStrip.qml`):
- `Island` singleton: player pick (first Playing wins, else last Paused-with-track), `mediaActive` stickier than raw playback — pause lingers 15 s (resume-from-bar affordance), player gone hides instantly. Priority queue slots in here later without touching presentation.

## 🚚 Distribution Readiness Assessment (2026-07-28)

Honest answer to "how ready are we for a download script + daily driving, vs the other shells". Measured, not guessed.

**Verdict: as a *shell*, genuinely competitive. As a *distributable*, at zero.** Feature parity is real — battery, tray, OSD, polkit agent, native lock screen, launcher with frecency + prefix modes, notification centre, 7-page settings app, matugen theming with terminal fan-out, first-run wizard. That list holds up against any of the references. But not one of the things that turns a folder into something another person can install exists yet.

### What the references actually do

| | caelestia | ii-dots | iNiR | **wisp** |
|---|---|---|---|---|
| Distribution | **3 repos** (shell + CLI + dots), AUR `caelestia-shell`, cmake install | monolithic `./setup` with subcommand dispatcher + `sdata/` lib, multi-distro (arch/fedora/gentoo/nix) | `Makefile` + **3 PKGBUILDs** (meta / shell / shell-git) + AUR publish script | **none** |
| CLI | separate `caelestia-cli` repo | — | `inir` (run/settings/welcome/restart/logs/status/doctor + IPC targets) | **none** |
| Autostart | Hyprland `exec-once` from the dots repo | dots repo | systemd user unit (`make install-systemd`) | **none** |
| Nix | `flake.nix` | `sdata/dist-nix` | `flake.nix` | — |

Note on the fastfetch preset: it is **not** in caelestia's shell repo — it lives in their separate main *dots* repo. That distinction matters here (see below).

### Hard blockers, in order

1. **Not a git repository.** `git rev-parse` fails. Nothing can be cloned, tagged, versioned, diffed or packaged. Everything else on this list is downstream of this one.
2. **No LICENSE.** Unpublishable as-is.
3. **State is written into the shell directory.** `settings.json`, `colors.json`, `events.json`, `app_usage.json` and `generated/` all live next to `shell.qml` via `Quickshell.shellPath(...)`. Fine for clone-and-run; **fatal for any system package**, where the install dir is root-owned and read-only. Needs an XDG split — code in the install dir, state in `$XDG_STATE_HOME`/`$XDG_CONFIG_HOME`. This is the one blocker that requires touching real code, and it gets more expensive the longer it waits.
4. **No autostart.** Nothing puts wisp into a session.
5. **Exactly one keybind, injected at runtime, wiped by every `hyprctl reload`.** Super+Space is the shell's only bind and it evaporates on any config reload. A daily driver needs binds that survive.
6. **The sandbox contract is the wrong contract for a daily driver.** "Never write dotfiles, runtime-only injection, coexist with the user's real shell" was exactly right while developing *alongside* ii — and it is why items 3–5 are unsolved. A shell you actually daily-drive has to own the session. **This is an architectural fork, not a chore**, and it needs a decision before the installer is written.

### What is already better than expected

- **Zero hardcoded `/home/dzejkop` paths** anywhere in `*.qml`/`*.sh` (the wallpaper-folder fix removed the last one).
- **Nothing writes outside the project directory** — the sandbox contract genuinely holds.
- **ii coupling is fallback-only and degrades gracefully**: reading ii's wallpaper state file is a *last* fallback after `Theme.dynWallpaper` and `Settings.lastWallpaper`, and the kitty fan-out only touches ii's generated file if it exists. On a non-ii machine these are no-ops, not errors.
- **Dependency surface is small and ordinary** (by call count): `hyprctl`, `kitty`, `matugen`, `jq`, `hypridle`, `swww`/`hyprpaper`, `bc`, `wl-copy`, `qalc`, `xdg-user-dir`, `nvidia-smi`, `xdg-open`, `loginctl`/`systemctl`, `curl`, `python3`, `wpctl`/`pactl`. Plus `quickshell`, a Nerd Font and Google Sans Flex. No compiled plugin, no build step — a real advantage over caelestia (cmake + C++ + `libcava` + `aubio`).
- **Two CLI subcommands already exist in substance**: the welcome wizard's system check *is* `doctor`, and `FirstRun.showAgain()` *is* `wisp welcome`. They need a headless entry point, not new logic.

### Recommendation

**Build the CLI, skip the fastfetch preset for now.**

- A `wisp` CLI is cheap and high-leverage: it gives the installer a smoke test (`wisp doctor`), gives the user a stable way to start/restart/inspect, and replaces every "run `qs -p …/settings.qml`" in the docs with one word. iNiR's surface (`run`/`settings`/`welcome`/`restart`/`logs`/`status`/`doctor`) maps almost 1:1 onto what wisp already has, and `doctor` can reuse the dependency probe already written for the wizard's last step.
- A **fastfetch preset belongs to a dots layer that does not exist yet** — caelestia keeps theirs in their dots repo, not the shell repo, for exactly this reason. wisp is currently a *shell*, not a *dotfiles distribution*. Adding a fastfetch config now means either shipping it from the shell repo (wrong layer, and it would have to write to `~/.config/fastfetch`, breaking the sandbox contract) or creating the dots repo first. It is a nice touch and costs an hour — just not before items 1–3.

**Suggested order**: `git init` + LICENSE + `.gitignore` + README → XDG state split (item 3) → decide the sandbox fork (item 6) → `wisp` CLI → install script / PKGBUILD → autostart + persistent keybinds → dots repo (fastfetch, hyprland config, etc.).

### Housekeeping surfaced by this audit
- `test.qml` is a stray probe that does not follow the `test_*` naming convention — 20 probes total would otherwise ship in a package. A `.gitignore`/install manifest has to exclude them.
- `core/Settings.qml`'s header comment still describes the sandbox contract in terms of "this machine runs illogical-impulse" — needs rewriting once item 6 is decided.

## 📦 Scaling Notes — Packaging This as a Distro Shell

Things that work fine for a single dev machine but will break or embarrass on someone else's install:

- **No hardcoded personal paths.** Wallpaper folder (see Known Bugs #4) is the current offender; audit for others before packaging (this file's own dir path in `plan.md`/scripts is fine since those are dev-only).
- **Font is assumed present, not verified.** `"Iosevka Nerd Font"` is hardcoded in ~20+ places across every component. For a distro, either ship the font as a hard package dependency and check it's installed on first boot, or centralize it as `Theme.fontFamily` so a missing-font fallback / user override is one line, not twenty.
- **`nvidia-smi`/`bc` are unverified external dependencies.** `sysmon_snapshot.sh` degrades gracefully today (`|| echo 0` fallback works whether the binary is simply missing or genuinely returns nothing), but the GPU ring in `PerformanceCard.qml` still renders permanently at 0% on non-Nvidia hardware instead of hiding itself — on AMD/Intel-only machines that's a ring that's always empty and confusing, not absent.
- **One `Process`-per-widget polling model won't scale.** `PerformanceCard.qml` embeds its own `Process` running an infinite bash loop. If more widgets each spawn their own poller (battery, network throughput, disk I/O), that's N always-running bash loops. Consider one central `SystemMonitor` singleton (same shape as `core/Audio.qml`) that all consumers bind to, with a single poll loop.
- **QT theming (kde-material-you-colors) blocked on a missing system dependency, not a code issue.** User approved adopting `kde-material-you-colors` (already installed, `kde-material-you-colors-git 2.2.0`) as the QT/Kvantum theming backend over building a from-scratch qt5ct/Kvantum template. Tested live (`kde-material-you-colors --file <wallpaper> --dark --manual-fetch`): crashes with `ModuleNotFoundError: No module named 'magic'` — `python-magic` is genuinely not installed (`pacman -Qs python-magic` → nothing), a gap in this AUR package's dependency chain on this machine, not something qmlshell's code can work around. Confirmed this system already has `kde-material-you-colors`' *output* in place though (`~/.config/Kvantum/kvantum.kvconfig` → `theme=MaterialAdw`, generated `qt5ct`/`qt6ct` color files present) — it ran successfully at least once before, likely via ii's own setup, so this is purely a "reinstall/repair the dependency" problem, not a design problem. **Deferred**: fix needs `sudo pacman -S python-magic` (or correct package name — verify first), which the user wants to hold off on until the install/packaging script below exists, so it gets declared as a proper dependency instead of hand-fixed on this one dev machine.
- **Install/packaging script — deferred until real-hardware testing.** User's plan: once the shell is feature-complete, write a proper install script that packages every dependency (matugen, kde-material-you-colors + python-magic, kitty, fonts, whatever else has accumulated) and "puts everything everywhere" — a real first-run installer, not just this dev machine's ad-hoc state. Explicitly scoped as a *later* task, done when the user starts using these dotfiles as their actual daily driver on their own PC (this machine currently dual-runs `ii` as the real daily shell alongside this project for dev/testing). Ties directly into the existing "No first-run experience" bullet below — same underlying gap, this is the concrete plan for closing it.
- **No first-run experience — ✅ mostly closed (2026-07-28)**, see the First-Run Welcome Wizard section above. `welcome.qml` now runs once on a fresh machine (gated by `shell.welcomeSeen`) and its last step performs the dependency + font check this bullet asked for. Still open from the original ask: the check *reports* a missing GPU/binary rather than acting on it — the GPU ring in `PerformanceCard.qml` still renders at a permanent 0% on non-Nvidia hardware instead of hiding itself (see the `nvidia-smi`/`bc` bullet above), and nothing yet writes a tailored default `settings.json` beyond the declared JsonAdapter defaults.
- **GTK/QT/portal/cursor/file-manager are OS-config, not shell code** (research 2026-07-27, see Full-Shell Roadmap above) — install-doc checklist for whatever installer/README this project eventually ships, not a qmlshell task:
  - `qt.platformTheme = qt6ct` + Kvantum engine for Qt apps to pick up the theme at all.
  - `xdg-desktop-portal` backend: pick `hyprland` or `gtk`, and explicitly route the filechooser portal to `kde` or `gtk` so a plain Dolphin/Nautilus/GTK file-picker dialog works without any custom qmlshell integration.
  - GTK3/4: `gtk.css`/`gsettings` dark-mode + accent color, ideally sourced from the same matugen run once Big Future Task #4 lands.
  - Cursor theme: any `hyprcursor`/xcursor theme set via `hyprland.conf` env vars — not something qmlshell needs to touch.
  - File manager: no reference repo solved this well (nixos-configuration has none configured at all, relies on GNOME's session; ii-dots just relies on the portal routing above) — don't over-invest here, "install thunar/dolphin + route the portal" is sufficient, no deep in-shell integration needed.

## 🎮 osu!lazer Island Widget — ✅ BUILT (2026-07-29)

New dynamic-island activity, sibling to media/notif, sourced from the user's own `ppeek` overlay project's data path (tosu's v2 websocket) rather than any Quickshell-native service — tosu is a standalone memory-reader binary, there is nothing native to bind to.

**Pipeline**: `core/Osu.qml` (new singleton) runs `scripts/osu_connect.js` as a `Process`+`SplitParser` — a small reconnecting Node client (Node's built-in `WebSocket`, stable since Node 22, chosen specifically to avoid adding a pip/npm dependency to a project with no package-manager step) that subscribes to `ws://127.0.0.1:24050/websocket/v2` and emits one compact JSON line per tick, parsed straight into `Osu`'s properties (`username`, `globalRank`, `profilePp`, live `livePp`/`combo`/`accuracy`/hit counts, `state`). `core/Island.qml` arbitration extended: osu outranks media while `Osu.active` (live PP/combo is more time-sensitive than a song title), and gained an `activeWidth` property so `shell.qml`'s collapsed-pill width binding can grow for the wider osu face (`Osu.inGameplay ? 620 : 540`) instead of the previous flat `540`. `components/IslandOsuStrip.qml` (new) renders two faces swapped on `Osu.inGameplay`: idle profile card (avatar via `https://a.ppy.sh/{userId}`, username, global rank, total PP) and a live scoring HUD (PP, combo, accuracy, 300/100/50/miss), mirroring `IslandMediaStrip.qml`'s conventions.

**🔴 Real socket-leak bug found and fixed during live testing.** `osu_connect.js`'s reconnect logic registered `scheduleRetry` on both the WebSocket's `"close"` and `"error"` events — but a failed handshake fires **both** for the same attempt, so every failure scheduled two independent retries, doubling the number of pending reconnect attempts each cycle (2→4→8→…→1024) until the process hit its default 1024 open-file-descriptor `ulimit` and plateaued. That plateau then exhausted the ephemeral port range specifically for `127.0.0.1:24050` (`ss -tan | grep 24050 | wc -l` → ~39590 entries), which blocked **all** new connections to tosu, including unrelated diagnostic tools — a two-line reconnect bug briefly took down the whole port. Fixed with a per-attempt `retryScheduled` guard flag plus an explicit `ws.close()` before scheduling. Also found and killed an orphaned duplicate `osu_connect.js` left over from an earlier `timeout N qs -p shell.qml` test run whose `timeout` hadn't propagated the kill to the child process — **lesson: `timeout` on a QML process does not reliably kill Process-spawned grandchildren; check `pgrep` after any timeout-bounded probe run.**

**🔴 The actual "nothing renders" bug was in tosu, not in wisp or in ppeek.** Both ppeek's own overlay and this new widget showed nothing even with osu!lazer visibly running and playing on screen. tosu's own log (`~/.local/share/tosu/logs/latest.log`) showed the real cause on repeat: `lazer Pattern scanning failed, retrying... Memory resolve failed`. Root cause: Linux's Yama LSM `ptrace_scope` defaults to `1` (restricted) — a process may only `ptrace`/read `/proc/pid/mem` of its own descendants unless it holds `CAP_SYS_PTRACE`. tosu is spawned as a **sibling** of `osu!lazer` (by ppeek's own `core/app.py` supervisor, not as its child), so this blocks tosu's memory read outright, independent of process-name detection (which was separately confirmed correct — verified directly inside the `osu-lazer-bin` AppImage that the actual apphost binary and `StartupWMClass` are both literally `osu!`, matching ppeek's `_OSU_NAMES` check). **Fix applied**: `sudo setcap cap_sys_ptrace+ep /opt/tosu/tosu` — grants tosu specifically the capability it needs without weakening `ptrace_scope` system-wide. Confirmed working live: both idle face (username/rank/pp) and live-play face (pp/combo/acc/hit counts) render correctly, screenshotted by the user.

**Deployment note**: the live shell runs from `~/.local/share/wisp-shell` (populated by `setup`'s `cp -a`, not a symlink), separate from this dev repo — every file touched here had to be manually copied over and the live `qs -p shell.qml` process restarted before any of this was testable end-to-end.

## 💬 Discord Voice Island Widget — ✅ BUILT (2026-07-29)

Second "ambient app presence" island lane after osu, but deliberately the **lowest**-priority one: `core/Island.qml`'s `current` now resolves `notif > osu > media > discord > none`. Being in a call is a long-lived ambient fact, not a moment, so anything with actual content takes the strip back off it. `activeWidth` gains a `460` case (narrower than media/osu — the face carries three short fields).

**Why Pipewire and not Discord RPC.** The obvious source, `/run/user/$UID/discord-ipc-0`, exists on this machine but is served by **arRPC** (Vesktop's bridge), which implements only the rich-presence subset — `SET_ACTIVITY` / `INVITE_BROWSER` / `DEEP_LINK`. There is no `GET_SELECTED_VOICE_CHANNEL` and no `VOICE_STATE_UPDATE` to subscribe to, and even on the official client those need the OAuth `rpc` scope. **Consequence: the server/channel name is not obtainable and the widget does not pretend otherwise.** What *is* reliable: a Discord client opens an audio **capture** stream only while connected to a voice channel. Its `Stream/Output/Audio` "Playback" node exists the entire time the app runs and is worthless as a signal; the capture node (`isStream && !isSink`) is the one that means "in voice".

**Pipeline**: `core/Discord.qml` (new singleton) scans `Pipewire.nodes.values` for a capture stream whose `properties["application.process.binary"]` is in a Discord-family allowlist (`vesktop`, `Discord`, `DiscordCanary`, `ArmCord`, `legcord`, …). Confirmed by probe (`test_pwstreams.qml`, new) that `PwNodeIface.properties` is a readable `QVariantMap` from QML — but only with a `PwObjectTracker { objects: Pipewire.nodes.values }` tracking *every* node, not just the default sink/source as `core/Audio.qml` does. Vesktop reports `application.name = "Chromium"`, so the process binary is the only usable discriminator. A 4s `drop` linger (same idea as Island's media linger) absorbs the capture-node teardown/rebuild that happens on input-device switch or Discord reconnect, which would otherwise flicker the island out mid-call. `elapsed`/`elapsedText` tick from a `Timer` gated on `inVoice` — no idle cost. `micMuted` is the capture node's own mute OR the default source's; **it is the system mic, not Discord's mute button**, which is software-side and never touches Pipewire — hence the icon is a plain mic, not a "Discord muted" badge.

**Detection confirmed live**: joining a voice channel adds exactly one node — `id=98 isSink=false name="Chromium input" binary=vesktop media.name=RecordStream media.class=Stream/Input/Audio` — alongside the (now three) permanent playback nodes. Leaving removes it. The `application.name`/`node.name` are both the useless `"Chromium input"`; `application.process.binary` is the only field that says Discord.

**🔴 "Pill grows but the strip is empty" was a stale-process artefact, not a layout bug.** Quickshell hot-reloaded the running shell as files were saved, and it picked up the new `core/Island.qml` arbitration (hence the widening to 460) **without** picking up the newly-added `components/IslandDiscordStrip.qml` — so the lane was selected but had nothing to draw. `ps -o lstart` on the live process was the tell: started 14:14:09, every touched file mtime 14:36–14:37. A cold `wisp restart` fixed it. **Lesson: a partial hot-reload can leave the shell in a state no cold start ever produces — check the live process's start time against file mtimes before debugging a "renders wrong" report.** Also: `pgrep -f "qs -p shell.qml"` finds nothing because the real cmdline is `qs -p /home/…/shell.qml` and the binary is `qs`, not `quickshell` — match on the absolute path.

**Three new probes** (`test_pwstreams.qml`, `test_discordisland.qml`, `test_collapsedbar.qml`) pin the three layers separately: which Pipewire nodes exist, what the strip measures/renders on its own, and what `CollapsedBar`'s `RowLayout` actually hands each lane at `Island.activeWidth`. The last two force the lane on by assigning `Discord.inVoice = true` — which is why `inVoice` is a plain settable property rather than a `readonly` binding off `capturing`. Steady-state and mid-run join transition both measured 169px visible; screenshot-verified via `grim`.

### Hover controls — mute / deafen / leave

Same interaction shape as the media strip's transport row: the label column crossfades out on hover and three spring-popped glyph buttons take its place, in a fixed-width `Item` so the pill does not resize under the cursor. Leave goes red on hover instead of accent — it's the destructive one.

**Command path**: there is no local API to drive a Discord client with, so the buttons deliver Discord's own in-app shortcuts to its window via Hyprland's `send_shortcut` dispatcher, which matches a window by regex and does **not** require focusing or raising it. Syntax had to be probed off the live compositor: the flat `hyprctl dispatch sendshortcut CTRL SHIFT, M, class:vesktop` form dies on the Lua parser (`')' expected near 'CTRL'`), and `hl.dsp.sendshortcut` is nil — the real name is **underscored**, `hl.dsp.send_shortcut({ mods, key, window })`. Enumerating `hl.dsp` from Lua (`for k in pairs(hl.dsp)`, surfaced via `error()` since `hl.notify` doesn't exist) is the fastest way to get a dispatcher's real Lua name; calling it with no args makes Hyprland print its expected table shape.

Keys live in `Settings.conf.discord` (`muteKey`/`deafenKey`/`leaveKey`/`windowMatch`), defaulting to Discord's factory `CTRL SHIFT, M` and `CTRL SHIFT, D`. **Disconnect has no factory shortcut in Discord** — `leaveKey` defaults to `CTRL SHIFT, L` but the user must bind "Disconnect From Voice Channel" to it under Discord Settings → Keybinds. An unset key dims its button rather than silently no-opping.

**Two honest limitations, both structural:**
1. **No readback.** `selfMuted`/`selfDeafened` are optimistic — they track what we told Discord, not what Discord did. Muting from inside Discord desyncs them until the next join. There is no channel to close the loop with.
2. **Tray-minimised Discord is unreachable.** Vesktop's tray minimise destroys the Wayland toplevel, so there is no Hyprland client for `send_shortcut` to match and the buttons do nothing (Hyprland's `window not found` warning goes to hyprctl's stdout, which `execDetached` discards). Confirmed: `hyprctl clients` lists no vesktop while it sits in the tray, even though the process and its Pipewire nodes are alive — which is exactly why the *detection* side uses Pipewire and not window state.

**Glyph codepoints must be looked up, not guessed.** `md-phone_hangup` is `U+F03F5`, not `U+F0620` — the guessed value rendered as a `→|` tab arrow. The reliable method is reading glyph *names* out of the font's cmap (`fontTools`, `md-phone_hangup` → codepoint) against `JetBrainsMonoNerdFont-Regular.ttf`, which is what `Theme.fontIcon` actually resolves to here.

**Hover states are screenshot-testable without a hand on the mouse**: `hl.dsp.cursor.move({ x, y })` parks the pointer over the probe window, then `grim -l 0`. (`hl.dsp.cursor` is a table, not a function — `.move` / `.move_to_corner`.) That is how the wrong hangup glyph was caught.

`components/IslandDiscordStrip.qml` (new): blurple badge glyph `󰙯` (nf-md-discord, U+F066F — coverage verified against `JetBrainsMonoNerdFont-Regular.ttf`, which is what `Theme.fontIcon` actually resolves to on this box; no Iosevka Nerd Font is installed despite CLAUDE.md's icon rule naming it), breathing green live dot, "Voice connected" + `m:ss`/`h:mm:ss`, mic/mic-off glyph. `Theme.blurple` added as a fixed brand colour rather than a palette-derived one, same reasoning as osu's pink.

## 🎮 Game Session Island Widget — ✅ BUILT (2026-07-29)

Third "ambient app presence" lane, and the first that carries its own transient. Priority sits directly under notifications: `notif > game > osu > media > discord`. A running game is the longest-lived thing the user is actually inside, and unlike osu it never has to fight for the strip to show its *events* — an achievement unlock swaps the game strip's own face for 6 s and falls back, so Island arbitration never sees it. `activeWidth` gains `530` (session face) / `620` (achievement face).

**What is and is not obtainable, established by probing this machine before writing anything:**
- **Detection is exact and needs no key.** Steam runs every launch through `reaper SteamLaunch AppId=<id>`, so the running app id is in the process cmdline — no window-class matching, no heuristics, native and Proton alike. Title comes from `appmanifest_<id>.acf`.
- **Cover art needs no key either.** `https://cdn.cloudflare.steamstatic.com/steam/apps/<id>/library_600x900.jpg` is public and unauthenticated (verified 200/image/jpeg for 367520), with `header.jpg` as the fallback. This matters because Steam's **local** art cache is useless for this: `appcache/librarycache/<appid>/` is hash-named (`f6ab055c…jpg`, `logo.png`, extensionless hashes), so there is no appid→cover mapping on disk. SteamGridDB is therefore only needed for launchers Steam's CDN does not cover (Heroic: Epic/GOG/Amazon).
- **Achievements have NO local source.** Checked directly: `userdata/<steamid>/<appid>/` contains only `remotecache.vdf` — there is no `stats/` directory anywhere under userdata, and `logs/stats_log.txt` logs per-AppID stat *syncs* (`Loading stats from disk...success`, `CAPIJobRequestUserStats`) without ever naming an achievement. The Steam Web API (`GetPlayerAchievements` + `GetSchemaForGame`) is the only way to know what unlocked, so achievements are gated on a free Web API key and a Public "game details" profile setting. `steamId` is auto-detected from `config/loginusers.vdf` (the block key *is* the SteamID64), so the user never has to look it up.
- **Cheap unlock latency without hammering the API**: `logs/stats_log.txt`'s mtime changes when Steam syncs a game's stats, which is what an unlock triggers. Using it as the "something happened" signal turns a blind 60 s poll into a near-immediate one.

**Pipeline**: `scripts/game_watch.sh` (new) → `core/Games.qml` (new singleton) → `components/IslandGameStrip.qml` (new), same Process + `SplitParser` shape as `Osu.qml`/`osu_connect.js`. The script emits a session line only when the game's *identity* changes — QML derives the live timer from `startedAt` itself, so a heartbeat would be pure wakeups. `startedAt` is the game process's own start time (`/proc/<pid>/stat` field 22 against `/proc/stat` btime), so a shell restarted mid-session shows the true elapsed time instead of restarting the clock at zero. The script re-reads `settings.json` every tick rather than taking keys via argv/env: a key pasted into Settings takes effect with no restart, and the keys never appear in `ps`.

**🔴 `pgrep -f 'SteamLaunch AppId='` matches things that are not games.** Any shell whose *own cmdline mentions* the launch string matches too — a `bash -c`, a terminal running the game by hand, and (repeatedly, during this build) the test harness itself. The symptom is a game that never stops being detected, because the matching shell outlives the real process. Fixed by checking **argv[0]**, not the whole line: Steam's outermost process is literally `reaper`, so `basename argv[0] == "reaper"` distinguishes the launcher from anything merely talking about it, with a non-shell fallback for games started outside Steam. General lesson for this repo: any `pgrep -f` on a string that also appears in test commands will match the test.

**🔴 Orphaned pollers accumulate from killed probes.** Six `game_watch.sh` processes were found alive with PPID 1 after a handful of probe runs — Quickshell does not reliably reap a `Process` child when its shell is killed abruptly, and each orphan keeps polling forever (and would keep calling the Steam Web API once a key exists). This is the same family as the `timeout`-doesn't-kill-grandchildren note in the osu section, but it accumulates silently instead of leaking one socket. Fixed **in the script**, not the workflow: each loop iteration checks its own PPID and exits when reparented to 1. Two things had to be right for that to work — bash's `$PPID` is captured at startup and never updates after reparenting, and `/proc/self` inside a command substitution is the *substituted command's* process (whose parent is the script), so the check must read `/proc/$$/stat`. The first version used `/proc/self` and silently never fired.

**Probe-sizing, again**: `test_gameisland.qml` (new) first rendered the strip alone in a bare capsule, which made the pill look far too wide for its content — the strip shares its row with the workspace dots and the clock, so a strip-only probe measures a layout that never exists. Rewritten to render the real `CollapsedBar` at `Island.activeWidth`. Also note `settings.qml`'s window rule floats **every** `org.quickshell` window at 860×600, probes included, so a probe must size its content explicitly rather than `anchors.fill` the window.

**Glyphs looked up, not guessed** (per the Discord section's lesson): `md-gamepad_variant` U+F0297, `md-trophy` U+F0538, `md-steam` U+F04D3 — and `md-controller`, the obvious first guess, **does not exist** in `JetBrainsMonoNerdFont-Regular.ttf`.

**Fullscreen exception, by user decision**: games are the main reason a workspace is fullscreen, so a lane that hides exactly while you play would never be seen. `shell.qml`'s `container.opacity` now lifts `fullscreenOverride` while `Games.flashing` and the pill is collapsed (`achievementPeek`). Only the *visual* suppression is lifted — `mask` stays on `emptyRegion`, so the surface still takes no input and clicks continue to reach the game underneath.

**Verified live**: cold `wisp restart`, then a synthetic `reaper SteamLaunch AppId=367520` process — the pill widened to 530, showed the Hollow Knight cover from Steam's CDN, the title, a ticking `0:12`, and the Steam badge; on process exit the lane cleared and media correctly took the strip back. Both faces screenshot-checked at true size via the probe. The achievement counter is correctly *absent* rather than `0/0` when no key is configured, same principle as the battery/GPU-ring rule.

**Not verified, honestly**:
1. **Achievement unlocks end-to-end** — needs a Steam Web API key (user is providing one) and an actual unlock in a running game.
2. **The fullscreen achievement peek** — same pre-existing limitation as the OSD's fullscreen suppression: `hasFullscreen` cannot be reliably flipped from `hyprctl eval` on this host, and it also needs a real unlock to coincide with a real fullscreen game.
3. **Heroic** — Heroic has **never been launched on this machine**, so there is no `~/.config/heroic` to read and no live process to match. `detect_heroic()` is written to fail closed (only claims a wine/proton process whose `HEROIC_APP_NAME`/`WINEPREFIX` actually points at a Heroic prefix), so the worst case is "no game detected" rather than a false one — but it is unverified guesswork until someone launches a game from it. `detect_gamemode()` (via `com.feralinteractive.GameMode`'s `ListGames`, only queried when `gamemoded` is already running so it never activates the daemon) is the catch-all for Lutris/Bottles/custom launches, and is equally untested.

**Deliberately no hover controls.** Every other strip's buttons drive something real (Discord's own shortcuts, MPRIS transport). A game exposes no local control surface worth pretending about, so this lane is read-only — clicking only dismisses an achievement flash early.

**Settings**: `settings.json` gains a `games` block — `enable`, `steamApiKey`, `steamId` (empty = auto-detect), `steamGridDbKey`. No settings-app page yet; the keys are hand-edited (or pasted via the settings app's "Config file" button) for now.

**🔴 Achievements were silently dead on the user's real config — `@tsv` + `read`.** With both API keys pasted in, nothing ever fired. Cause: `read_conf` parsed four settings with `jq -r '[...] | @tsv'` piped into `IFS=$'\t' read -r STEAM_KEY STEAM_ID SGDB_KEY ENABLED`. Tab is an IFS **whitespace** character, so `read` collapses a run of tabs into a single delimiter — and `steamId` is normally *absent* (it auto-detects from `loginusers.vdf`), so its empty field vanished and every later value shifted left: `STEAM_ID` received the SteamGridDB key. The Web API was then called with a garbage steamid, returned an error object with no `.achievements`, and the parser's `jq -e` guard treated that exactly like "nothing to report". No error surfaced anywhere — the same silent-failure shape as the `Qt.resolvedUrl` bug. Fixed with `mapfile -t` over one-value-per-line jq output, which preserves empty fields. **Lesson: never use `@tsv` + `read` for records with optional fields; `mapfile` over newline-delimited output is the only form that keeps empties.**

**Verified against the real Steam Web API** (key configured 2026-07-29, profile "Game details" public): `GetPlayerAchievements` returns real data (Hollow Knight 3/63, Terraria 100/137). The full emit path was exercised by running a copy of the script with the baseline poll stubbed out, so every already-unlocked achievement is treated as new — real display names, descriptions and icon URLs came through (`Charmed`, `Falsehood`, `Test of Resolve`). The unmodified script on the same game correctly emits `3/63` on the session line and **zero** achievement flashes, confirming the baseline suppresses history rather than replaying it at every launch. The achievement face was then screenshot-verified with a real schema icon URL rather than the glyph fallback.
